# Lab 13 寄存器与异常式故障教学重构设计

## 背景

Lab 13 当前直接要求学生构建不同故障场景，并使用 GDB 检查寄存器和指令。命令本身是正确的，但教学链条不完整：

- 学生尚未熟练阅读 RISC-V 汇编，不容易从 `ld a1, 0(a0)`、`jr t0` 或 `.word 0xffffffff` 推断程序行为；
- README 没有清楚说明三个场景分别破坏了数据访问、控制流和指令译码；
- 实验步骤更像命令清单，没有明确每条命令要回答的问题；
- `start.S` 缺少教学注释，学生无法把源码、寄存器状态和 GDB 观察连接起来；
- 执行故障指令后可能进入 trap 或难以解释的状态，但 README 没有充分解释为什么应当先在故障点停下。

目标读者已经完成 Lab 12，理解裸机启动流程，知道 `pc`、`sp`、`ra` 的基本用途，但还不能独立、流畅地阅读 RISC-V 汇编。

## 教学目标

完成 Lab 13 后，学生应当能够：

1. 用“取指、译码、执行”的最小模型解释 CPU 如何使用 `pc`；
2. 按 RISC-V 的操作数顺序阅读本实验使用的常见指令；
3. 从一条 load 指令中找出基址寄存器并计算有效地址；
4. 解释间接跳转如何由寄存器中的地址决定下一条指令；
5. 解释非法指令与坏内存地址是两种不同的故障；
6. 在执行可疑指令前，用 GDB 检查当前指令和关键寄存器；
7. 针对不同故障选择 `info registers`、`x/i $pc`、寄存器打印和反汇编等证据；
8. 用自己的话说明每个 scenario 为什么会产生相应现象，而不仅是复现命令。

## 采用的教学结构

采用“概念 → 汇编 → 实验闭环”结构：

```text
建立 CPU 与寄存器的最小模型
    -> 学会阅读本实验所需的少量指令
    -> 预测三个故障场景
    -> 在故障指令执行前暂停
    -> 用 GDB 验证预测
    -> 解释观察结果
```

不改变 scenario 名称、Makefile 命令或程序行为。此次工作是教学材料重构，不扩展为 trap handler 实现或启动代码重写。

## README 设计

README 使用中文教学正文，保留英文命令、指令名、寄存器名和必要的体系结构术语。

### 1. 开场与 Lab 12 衔接

开头先回答“这个实验在干什么”：

> Lab 12 观察 CPU 如何进入我们自己的程序；Lab 13 人为制造三类低层错误，练习从当前指令及其使用的寄存器找到原因。

随后给出本实验的核心调试问题：

```text
pc 指向哪条指令？
这条指令读取哪些寄存器？
这些寄存器中的值是否合理？
```

### 2. Concept Warm-up

预热部分只覆盖完成实验所需的汇编知识，避免发展成完整的 RISC-V 教程。

内容包括：

- CPU 的“取指—译码—执行”最小模型；
- `pc` 与当前待执行指令的关系；
- label 是地址的名字，而不是会自动执行的特殊语句；
- RISC-V 常见的 `destination, source` 阅读方式；
- 本实验中的 `a0/a1`、`t0–t3`、`sp` 和 `ra`；
- `a*` 与 `t*` 都是 caller-saved 寄存器，但本实验只要求理解函数调用可能改写它们；
- `la`、`li`、`mv`、`ld`、`lbu`、`sb`、`addi`、`andi`、`beqz`、`j`、`jr`、`call`、`ret`、`wfi`；
- `ld a1, 0(a0)` 的有效地址计算；
- `jr t0` 如何把控制流交给 `t0` 中的地址；
- `.word 0xffffffff` 如何把原始位模式放进代码区，并在执行时触发非法指令；
- `.section`、`.globl`、`.equ`、`.asciz`、`.align`、`.skip` 的最低必要含义；
- GNU assembler 数字局部标签，如 `1:`、`1b`、`3f`。

### 3. 三类故障的对比

使用一张预测表并列展示：

| Scenario | 被破坏的对象 | 关键指令 | 关键寄存器 | GDB 要验证的事实 |
|---|---|---|---|---|
| `bad-pointer` | 数据访问地址 | `ld a1, 0(a0)` | `a0` | `a0 == 0xdeadbeef`，load 使用该地址 |
| `bad-jump` | 控制流目标 | `jr t0` | `t0` | 下一条指令地址来自 `t0` |
| `illegal-instruction` | 指令译码 | `.word 0xffffffff` | `pc` | `pc` 指向无法正常译码的位模式 |

同时明确 `bad-jump` 跳到的是“有效但出乎预期”的 label，它用于展示控制流错误，不一定立即产生硬件 exception。

### 4. Guided Mode

每个实验步骤采用同一节奏：

1. 阅读即将执行的少量源码；
2. 写下或口头回答预测；
3. 在故障指令或跳转源处设置 breakpoint；
4. 使用 GDB 命令收集证据；
5. 将观察结果与预测对照；
6. 解释如果继续执行，原始线索为何可能变难观察。

每条 GDB 命令旁说明它回答的问题。例如：

- `x/i $pc`：CPU 接下来准备执行什么；
- `p/x $a0`：load 的基址是多少；
- `info registers pc t0`：间接跳转的起点和目标依据是什么；
- `x/10i $pc`：当前指令附近的控制流长什么样。

先运行 `good` scenario 验证工具链，再依次完成 `bad-pointer`、`bad-jump` 和 `illegal-instruction`。

### 5. Trap 边界说明

README 解释：

- 本实验在 M-mode 运行，但没有安装完整的 trap handler；
- 执行坏 load 或非法指令后，CPU 会更新相关 CSR 并转向 `mtvec` 指定的位置；
- 由于本实验没有建立可供学生依赖的 handler，继续执行后的现场可能因 QEMU 行为和当前状态而难以阅读；
- 因此主要方法是在可疑指令执行前停下，通过指令和输入寄存器证明根因；
- `mcause`、`mepc`、`mtval` 作为补充观察，不假定所有环境中都能在继续执行后稳定停留在同一位置。

QEMU `int,cpu_reset` log 作为补充证据，而不是主要学习路径。

### 6. 总结与复习

结尾采用“你现在应该能解释”式检查，包括：

- 为什么仅看到 `0xdeadbeef` 不足以证明错误，必须结合使用它的指令；
- 为什么 `jr t0` 的下一条指令由 `t0` 决定；
- 为什么非法指令不是访问了坏地址；
- 为什么故障前现场通常比故障后现场更直接；
- 如何根据指令选择要检查的寄存器。

保留简短参考答案，便于学生自检。

## `start.S` 注释设计

`start.S` 保持现有执行行为，只增加中文教学注释并改善区块可读性。

注释按以下层级组织：

1. 文件头说明该文件同时承担启动、scenario 选择、UART 输出和故障制造；
2. 常量、预处理宏、section 与导出符号说明；
3. `_start` 对栈初始化、`call` 和返回后 halt loop 的说明；
4. `kernel_entry` 对 C preprocessor 条件编译的说明；
5. 每个 scenario 的“执行前状态—关键指令—预期结果”；
6. `uart_puts` 的参数、临时寄存器、轮询流程和数字局部标签；
7. `.rodata` 与 `.bss` 中字符串和栈空间的说明。

注释重点解释“为什么”，避免把每条明显指令机械翻译成中文。对初学者不直观的伪指令和寻址形式则逐条说明。

## 验证

实现后进行以下检查：

1. 对照 README 与源码，确认 label、scenario、命令和 build 路径完全一致；
2. 搜索所有 GDB 命令，确认寄存器名和 breakpoint symbol 存在；
3. 构建四个 scenario：

   ```bash
   make SCENARIO=good
   make SCENARIO=bad-pointer
   make SCENARIO=bad-jump
   make SCENARIO=illegal-instruction
   ```

4. 检查反汇编，确认注释修改没有改变指令路径；
5. 若本机工具链可用，运行 `good` 并对三个故障场景进行最小 GDB 验证；
6. 若工具链缺失，明确报告未运行的验证，而不把静态检查描述为运行成功。
